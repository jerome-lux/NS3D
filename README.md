# NS3D

Steady, incompressible, low-Reynolds Navier-Stokes flow solver for a
porous medium described by a binary 3D image (0 = fluid, 1 = solid).

The program computes the Darcy permeability of the microstructure by
solving the momentum and continuity equations on a staggered grid with
a SIMPLE-family pressure-velocity coupling.

Four outer-loop algorithms are provided:

| algorithm | description                                             |
|-----------|---------------------------------------------------------|
| `SIMPLEC` | SIMPLEC: pressure correction with the SIMPLEC matrix    |
| `SIMPLER` | pseudo-velocity based, N1 inner pressure iterations     |
| `SIMPLERR`| SIMPLER plus a final pressure update per outer iteration|
| `IDEAL`   | double pressure-update loop (N1 + N2 inner iterations)  |

## Dependencies

- C++11 compiler (GCC / Clang)
- CMake (>= 3.16)
- Eigen3 (header-only, >= 3.3)
- Blitz++ (3D arrays)
- VTK (reading/writing `.vti` images)
- OpenMP (optional, for the parallel loops)

### Debian / Ubuntu

```sh
sudo apt install build-essential cmake g++ \
    libeigen3-dev libblitz-dev libvtk9-dev
```

> The build requests only the VTK components it uses
> (`CommonCore CommonDataModel CommonMath ImagingCore IOCore IOLegacy
> IOXML`), so the Qt-dependent GUI modules are **not** pulled in and
> `qt6-base-dev` is **not** required — even though the Ubuntu VTK 9
> packages are built with Qt enabled. If your distribution provides
> VTK 6 or VTK 8 instead of VTK 9, install the matching
> `libvtk*-dev` package. The code supports VTK >= 6.

### Other systems

- **Eigen3** and **Blitz++** are header / template libraries, so any
  current release works.
- **VTK** must be installed with CMake support (the CMake config files
  shipped by the package are used).
- The code uses the `#include <eigen3/...>` form, so the Eigen include
  directory must be the *parent* of the `eigen3/` folder (this is the
  default layout of the Debian/Ubuntu `libeigen3-dev` package).

## Build

```sh
mkdir -p build
cd build
cmake ..
make -j$(nproc)
```

The executable is `build/NS3D`.

To install it (optional):

```sh
sudo make install     # from the build directory
```

## Run

```sh
./NS3D sample.ini
```

A complete, commented example is provided in [`sample.ini`](sample.ini).
To list every accepted key and its meaning, run:

```sh
./NS3D -h
```

### Input file

The input file is a simple `key = value` text file:

- keys are case-insensitive;
- blank lines and lines starting with `#` are ignored;
- an inline `# ...` comment is allowed after a value;
- unknown keys are reported as a warning;
- a malformed value (or a missing required key) is a fatal error;
- after parsing, the effective parameter set is printed so you can
  confirm what will be used.

### Outputs

For an input image `<image>` and flow direction `<dir>`, the program
writes:

- `INFO-<dir>-<image>.log` - human-readable run log;
- `RES-<dir>-<image>.csv`  - per-iteration convergence log
  (flow rate, permeability, residuals, solver iterations);
- `P-<dir>-...`, `Vx-<dir>-...`, `Vy-<dir>-...`, `Vz-<dir>-...`,
  `V-<dir>-...` `.vti` files - the pressure and velocity fields
  (open with ParaView or any VTK-capable viewer);
- `...-SAVE-<n>.vti` - snapshots saved every `save_step` iterations.

## Testing

A small CTest suite exercises the full pipeline (image → index arrays →
solvers → Darcy permeability) on a reproducible benchmark geometry: a
128³ binary image of non-overlapping spheres (0 = fluid, 1 = solid),
generated by `src/gen_spheres.cxx` into `data/spheres_128.vti`.

From the build directory:

```sh
cmake --build . --target make_test_images   # (re)generate data/*.vti
ctest --output-on-failure                   # run the whole suite
```

The solver outputs written during a run (`INFO-*.log`, `RES-*.csv`,
`P-*`, `V*`, `*-SAVE-*.vti`) and the per-algorithm logs
(`cmp_*.log`) are git-ignored.

| test               | what it does |
|--------------------|--------------|
| `gen_spheres_image`      | regenerates `data/spheres_128.vti` (keeps `ctest` self-contained) |
| `gen_spheres_image_64`   | regenerates `data/spheres_64.vti` |
| `test_spheres`           | 128³, SIMPLEC: runs the full pipeline and requires a positive, finite Darcy permeability |
| `compare_algorithms`     | 64³: runs all four algorithms and compares K, iterations, time and convergence |

### Single-geometry test (`test_spheres`)

Runs the solver on the 128³ image. The iteration budget in
`tests/test_spheres.ini` is intentionally modest (30 outer iterations,
≈ 1–2 min on a few cores); raise `maxitSIMPLE` for a converged
reference value.

### Algorithm comparison (`compare_algorithms`)

`tests/compare_algorithms.sh` runs the SAME 64³ setup with each of the
four outer-loop algorithms (only the `method` line differs) and prints a
side-by-side comparison. The 64³ image is used so that a full
convergence check (up to 200 outer iterations) is affordable. Timing is
pinned to 4 OpenMP threads so the comparison is fair. A representative
run:

```
method              K (m^2)      iters     time (s)    converged
--------           --------      -----     --------    ---------
SIMPLEC         3.28386e-12         48        5.435          yes
SIMPLER         3.28382e-12         42        8.033          yes
SIMPLERR        3.28175e-12         23        5.690          yes
IDEAL           3.28212e-12         19        2.788          yes
Converged (RMR < simpletol): 4 / 4
```

All four algorithms agree on the permeability to < 0.1 %, which
cross-validates the implementations; the differences are in the
number of outer iterations and the wall-clock time.

## Documentation

A self-contained reference of the numerical methods is provided in
`doc/`:

| file | content |
|------|---------|
| `doc/NS3D_methods.tex` | LaTeX source |
| `doc/NS3D_methods.pdf` | compiled document |

It describes the governing equations, the finite-volume discretization
on the staggered grid, under-relaxation, boundary conditions, the
pressure–velocity coupling (SIMPLE / SIMPLEC / SIMPLER / SIMPLER-R /
IDEAL), convergence control, the derived quantities (Darcy permeability,
RMR) and the full notation.

> **Disclaimer:** the methods documentation in `doc/`, the in-code
> docstrings and this README were written with the assistance of an AI
> language model (Qwen 3.8 27B).

## Parallel execution

Set the number of OpenMP threads before launching:

```sh
OMP_NUM_THREADS=8 ./NS3D sample.ini
```

Use the number of physical cores (not hyper-threads) for best
performance.
